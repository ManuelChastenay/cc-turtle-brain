# CC Turtle Brain

LLM-driven automation for ComputerCraft turtles, written in plain CC: Tweaked Lua.
A cheap LLM (via OpenRouter) plans; deterministic Lua executes.

## Environment
- Minecraft server on a managed host (gamesservers.io): no shell, file manager only.
- CC: Tweaked `computercraft-server.toml` has an `[[http.rules]]` entry for `openrouter.ai` with `timeout = 120000`.
- LLM access is API-based through OpenRouter (OpenAI-compatible endpoint). Subscription-based access was ruled out (would need an external bridge).
- Single player/user; designed for one turtle now, a fleet later.
- GPS works on the user's turtle (wireless modem + GPS hosts).
- Fuel can be turned off server-wide with `need_fuel = false` under `[turtle]` in `computercraft-server.toml`. Turtles then report `"unlimited"` and the code skips all fuel logic (tested). Not set as of 2026-10-03.

## Design: plan once, execute in Lua
- One LLM call per goal: the model sends the whole job as a plan (an ordered list of skill steps) through the single `runPlan` tool. Lua runs every step with no LLM call in between.
- The LLM is called again only when a step fails; it gets the error plus fresh state and sends a plan for the rest, or explains. `maxTurns` caps this.
- A successful plan ends the run with a Lua-written summary (no "done" round trip).
- Status (position, facing, home, fuel, inventory, adjacent chest) goes in the first user message, so the model never spends calls on status tools.
- Not free-form Lua from the LLM: plans are data, so they are validated before anything moves, cost few output tokens, can't break the world outside skill rules, and can be split across turtles and sent over rednet.
- Fleet: same flow on a computer (`fleet`). The LLM sends `runPlans`: groups of turtle ids, each with steps. Lua splits shared steps (a skill's `split`: `mineBox` slices, `mineCircle`/`mineSphere` shares, `buildSphere`/`buildBox` tiles) inside a group, sends every turtle its steps, and waits for all of them. Only then, if any failed, the LLM is called again with every turtle's outcome and fresh state.
- Jobs survive reboots (server restart, chunk unload): turtles save their job and checkpoints to disk and carry on from the last one; the brain saves the job in flight and `fleet resume` waits for it again. See "Resume" below.
- Dashboard (`fleet dash`): the brain stays up as a screen. An advanced monitor shows every turtle (state, position, fuel, current step) and the event log, with touch buttons (STOP ALL, HOME ALL, REFUEL ALL, SET HOME, a stop per busy turtle; SET HOME needs a second tap within 5 s, the button turns into CONFIRM?). The terminal's last line is a prompt: plain text is a goal (same flow as `fleet <goal>`), `/commands` (`/stop [id]`, `/home [id]`, `/refuel [id]`, `/sethome [id]`, `/update [id]`, `/resume`, `/scale`, `/clear`, `/exit`, `/help`) run in Lua with no LLM call. `/exit` (or Ctrl+T) hands the terminal back to the shell; turtles keep working. Coroutines under `parallel` (listener, ticker, screen, keyboard, touches, runner, exit); the blocking `http.post` only stops the runner. The ticker polls turtles with a `quick` hello every 5 s.

## Files
- `install.lua`: downloads/updates all files from GitHub. Public repo uses raw URLs; private repo uses the GitHub API with a token in `/.github_token`. Add new files to its `FILES` list. Versions: `install` asks the GitHub API for the newest commit on main (`commits?per_page=1`; the `Link` header's last page = commit count = `n`), prints `Version v8 d2ffe09 (date)` and the commit message, downloads every file at that sha (no mixed files, no raw-cache staleness), and saves `/.version` = `{ n, sha, date, message }` only after every file is in. Same sha already installed: nothing downloaded (`install force` overrides). `install <sha>` installs a commit, short sha too: looked up with the same API call (`commits?sha=<sha>`, which gives the full sha and n), because raw.githubusercontent.com only serves full shas (a short one is a 404). `install <full sha> <n>` makes no API call (what `fleet update` sends turtles); a full sha alone still installs when the API is down (n unknown). API down or rate-limited (60/h per server IP without a token): files from the branch, `/.version` deleted (version unknown). It fetches itself first (at the same ref) and, if changed, re-runs the new copy with `--updated` and the same arguments, so new `FILES` entries arrive in one run. Installers older than that (pre-2026-10-03) need `install` twice. When the new copy fails, the outer run fails too (`error("", 0)`), so `shell.run("/install.lua")` reports it (the worker's `update` relies on this). Standalone: it formats versions itself, the same way as `bot/version.lua`.
- `brain.lua`: single-turtle entry point (`brain <goal>`). System prompt, state line, `runPlan` wiring. `brain refuel` runs `nav.refuelAll()` with no LLM call.
- `fleet.lua`: fleet entry point on a computer with a modem (`fleet <goal>`, `fleet resume` after a reboot, or `fleet dash` for the dashboard; either can go in `startup.lua`). Fleet system prompt, discovery, `runPlans` wiring. No-LLM commands: `fleet refuel [ids]` (one `refuel` step for the idle turtles; a saved job is dropped first, like for a goal) and `fleet update` (this computer runs `/install.lua` first, then every turtle installs that same commit and reboots: one API call for the fleet; a failed install here leaves the turtles alone). Ctrl+T stops the busy turtles (in `dash` it only quits the dashboard).
- `worker.lua`: run on each fleet turtle from `startup.lua`. Two coroutines: one runs plans, one answers the brain (status, busy, stop, ack) and other turtles (`makeway`: moves aside only when idle). Saves each job with `bot/job.lua` and resumes it at boot. Sets `nav.onTurtleInWay` to send `makeway` to a blocking turtle. `update { sha, n }` (idle only; busy = refused, its job would resume under different code): answers `updating`, runs `shell.run("/install.lua", sha, n)` in the listener coroutine (a non-hex sha is dropped), answers `updated` (`updated to v9 ..., rebooting`), then `os.reboot()`; no reboot when it already runs that commit (compared with the `/.version` read at boot). Every status carries `version` (`"v8 d2ffe09"`).
- `llm/config.lua`: endpoint, model slug, key path, `maxTurns` (LLM calls per goal), `maxRetries`, `debugPath`.
- `llm/openrouter.lua`: HTTP client. `chat(messages, tools) -> message, usage | nil, err`. Retries on network errors, 429 and 5xx. Sends `provider.require_parameters = true` with tools. Writes the last raw response to `debugPath` (`/llm_last.json`) — first thing to read when a run misbehaves.
- `llm/agent.lua`: provider-agnostic tool-calling loop. `run(goal, tools, systemPrompt, onTool, stopped) -> text, stats | nil, err`. Calls in one turn run in order and stop at the first failure; a successful `final` tool ends the run. `stopped()` (optional) is checked before every LLM call; true returns `nil, "stopped"` (the dashboard's stop: no replanning).
- `bot/config.lua`: turtle-side settings (state file, fuel items, fuel kept when unloading, junk list, protected blocks, fuel margin, turtle waits and retries, max plan length). Lists are substrings except `junk`, which uses exact names (a substring would catch Create's `andesite_alloy`). Junk: cobblestone and mossy cobblestone with their stairs/slab/wall, cobbled deepslate, dirt, gravel, andesite, diorite, granite, tuff, netherrack, calcite, smooth basalt, smooth stone and its slab (vanilla has no other variants of these three), terracotta (plain, the 16 dyed and the 16 glazed, built by a loop over the dye colors), raw copper, plus XyCraft World's `xycraft_world:kivi` (name from a schematic's materials list; that kivi drops itself is assumed, not checked). Modded variants need adding by exact name.
- `bot/nav.lua`: position/heading (dead reckoning saved to `/nav_state.json` after every move and turn; GPS fix + heading calibration by stepping once at `init()`, see "Resume"), `step`/`dig`/`goTo` that dig through obstacles except protected blocks, fuel, `refuel(target)` (only `config.fuelItems`, one at a time) and `refuelAll()` (every slot, anything that burns, `turtle.refuel()` per stack: CC burns no more than fits under the limit). Another turtle in the way is never dug, nor `M.keep` (a block name, set by `bot/build.lua` while building, reset by `init`). `dig` looks again when what is there changes between its `detect`, `inspect` and `dig` (a tick each: a passing turtle seen by `detect` can be gone by the `inspect`); only a block still there after a failed dig is an error. Before 2026-10-05 that race failed mining with `cannot dig unknown: Nothing to dig here` (seen in-game with 32 turtles). `step` waits; every 3rd try the turtle with the higher computer id (read with `peripheral.call(side, "getID")`, a coin flip if unreadable) steps off the line, preferring a free cell over digging one. It waits there, then comes back to the same cell and facing, and `onTurtleInWay(id)` fires. It gives up after `turtleWaits` tries. `clear` (used for mining's up/down digs) only waits. `makeWay(from)` steps an idle turtle off the line. `turtleBlocked(err)` tells a turtle-in-the-way failure apart; `patiently(fn)` calls `fn(retry)` again after a 2-5 s pause while it fails that way, up to `config.turtleRetries` (10) more times (~5 min in all), then adds `(tried 11 times)` to the error. Mining and the travel skills (`goTo`, `move`, `goHome`) use it; plain `nav.goTo` does not.
- `bot/inv.lua`: free slots, inventory summary, `count(name)`, `take(name, side)` (fills the turtle from an adjacent inventory, keeps `name` and fuel, puts back the rest it took; suck takes chest slots in order, so the supply should hold only that block and fuel), `discardJunk(open)` (drops `config.junk` on a side with no inventory: one of `open`, the sides the caller just dug, else one that `detect`s empty, else a solid one; the side is picked only once a junk slot is found, since reading slots costs no tick and `detect` does), and unload into an adjacent inventory peripheral: drops junk, then `refuelAll`, then stores (keeps up to `keepFuel` fuel items, none with unlimited fuel); returns `true, moved, junked`. Junk is never stored: mining drops it after every cell, `travel` after a trip that dug something (`bot/skills.lua`), unloading before anything is stored.
- `bot/mine.lua`: `mineArea` (box relative to the turtle), `mineBox` (box between two world corners; enters from above its nearest top corner, ends there), `mineCircle` (a cylinder: center block x,z, diameter, levels y1..y2) and `mineSphere` (a ball: center x,y,z, diameter, optional `top`/`bottom` cut). Walks the middle of each 3-layer group digging up/down (1 move per 3 blocks), stays inside the shape, returns to its start point on success or failure. Boxes use the original frame layout (`layout`, explicit axis orders through dug space). Round shapes (`roundLayout`) use a `bot/shape.lua` shape in world coordinates (saved in the checkpoint) and a share = run of x columns (`shape.share` of per-column block counts, so shares hold about as many blocks; each turtle computes its own from hidden `part`/`parts`); rows run along z. In a ball a group's top or bottom layer can be wider than the walked middle one: that ring is walked on its own layer after the middle pass. Moves in round shapes use `walk`: a block at a time toward the target along an axis whose next block is inside the whole shape (not just the share), so it may cross others' shares. In a ball, cylinder or box, cut flat or not, such a step always exists (a step toward the center never leaves; if every step toward c moves away from the center, c is further out on each axis than the new block). The door is the top level's block on the middle row nearest the share: for a ball cut below its middle (the user's case: 200 wide centered y=100, only y<=75) that is the share's own edge column; a whole ball's top is its pole, which every share goes through. After every cell's digs it drops the cell's junk into a side it just dug (`bottom`, else `top`), so junk stays in the hole and never piles up. When full anyway it drops junk, then burns what burns (`refuelAll`), and only then unloads, at a chest next to the start or at home. A cell, the way out or a trip that another turtle kept blocked is retried (`nav.patiently`), first rejoining the route like after a reboot (`rejoin`: inside the shape, else a neighbour inside, else back to the start), so a turtle left beside its path by giving way never digs outside the shape. A last `discardJunk` before leaving catches leftovers (e.g. dug while rejoining after a reboot). Round layouts yield (`sleep(0)`) every 4,096 cells: one turtle alone on the 200-ball example lists ~430k cells (1.4 s in desktop Lua, more in Cobalt, and a lot of memory); a 1/32 share is ~15k (0.06 s). In a simulated 4x50x50 slice of mixed ground, junk dropping took trips home from 17 to 0 and fuel from 6.5k to 3.5k.
- `bot/skills.lua`: the skill list the planner sees, plus `state()` (the status line). `splitRound` (mineCircle, mineSphere) gives share k of n (n = min(turtles, diameter)) to the turtles sorted west to east. `splitBuild` (buildSphere, buildBox) sorts turtles along the longer side (`shape.axes`); for hollow/walls the `shape.lowHalf(n)` turtles furthest toward the low side across take the low half's shares. A step that is already a share (parts > 1) goes to the first turtle as it is. Requires nav/inv/mine lazily so a computer can load it for the catalog and `split` functions.
- `bot/plan.lua`: builds the prompt catalog, the step JSON schema and arg checks from skill declarations (args marked `hidden` are checked but left out of the catalog and schema; `optional` args have no default, may be left out and show as `name=none`); validates, runs and reports plans. `run(steps, onStep, journal)`: with a journal it starts from the saved step and hands each skill `ctx = { state, save }`.
- `bot/job.lua`: the worker's job on disk: `/job.json` (steps, current step, its checkpoint, results so far) and `/job_result.json` (last result, kept until the brain sends `ack`).
- `bot/net.lua`: rednet protocol (`ccbrain`) and message types (incl. `update` -> `updating`, `updated`); `open()` opens every modem, `send`, `broadcast`. A worker's `status` carries `fuel` (number or `"unlimited"`) and, with a job, `step`/`steps`/`text`; `hello { quick = true }` gets a status without `state` and `result`, to keep the dashboard's polls small. (Reading the inventory is not slow: in CC: Tweaked `getItemCount` and `getItemDetail` without `detailed` return at once; only turtle commands like dig, move, drop and refuel take game ticks.)
- `bot/fleet.lua`: brain side: `discover`, `describe`, `wait`, `outcome`, `loadRun`/`clearRun`, and the `runPlans` tool. Saves the job in flight to `/fleet_job.json` before sending plans. Waits with pings every 15 s: silent 60 s = "silent" warning, 600 s = lost. A status carrying a kept result for the job counts as its result; one with neither the job nor its result = restarted without it (a `quick` status never counts: a dashboard poll answered just before the plan arrived would look like that). Every result is acked. `idle(turtles, only)`, `runSteps(...)` (fixed steps through the `runPlans` handler with no LLM, then `clearRun()` so a later resume never asks the LLM about it; used by `/home`, `/refuel`, `fleet refuel`) and `update(ids, target, onEvent)` (sends `target`'s sha and n, nil = each turtle the newest; an id silent for `UPDATE_ACK` = 5 s = an older worker without `update`; installs get `UPDATE_WAIT` = 180 s).
- `bot/dash.lua`: the dashboard daemon (see Design). `run({ system, skills, scale, shell })`. Logs its own version at start (`dashboard up ..., v8 d2ffe09`). A goal runs through `agent.run` with a `runPlans` whose handler refuses to start after a stop; `/home` stops busy turtles, waits until the registry shows them idle (15 s), then sends one `goHome` plan. `/refuel`, `/sethome` (and the SET HOME button) and `/update` take the idle turtles (all, or one id) and are refused while a job runs; `/update` runs `/install.lua` on this computer first (`installing` stops terminal drawing so the installer's output shows; the monitor keeps updating), then the turtles get that commit; the dashboard runs its old code until `/exit` and `fleet dash`. On exit (`/exit` queues `dash_exit`, or Ctrl+T) the terminal and monitor are cleared with a one-line note. A saved job is resumed at start. Draws into `bot/ui.lua`'s layout on the monitor, or on the terminal's top rows without a monitor; its own line editor (char/key/paste events, history) instead of `read()`, so one coroutine owns the screen.
- `bot/ui.lua`: pure drawing: `layout(view, w, h)` gives exactly `h` rows of colored chunks, each `w` wide, plus the touch buttons; `draw(term, view)` writes them (colors only when `isColor()`), `hit(layout, x, y)` maps a `monitor_touch` to an action. Columns shrink with the width: the stop button, then name, then position are added while the step column keeps 8, 12, 14 characters (about 39 wide shows no name or position: use text scale 0.5). The button bar needs 45 columns for full labels; narrower it uses short ones (`[STOP ALL] [HOME] [FUEL] [SETHOME]`, 34) and leaves out a button that does not fit. `view.confirm` swaps SET HOME's label for CONFIRM?.
- `bot/version.lua`: `read()` the installed version from `/.version` (nil if unknown), `text(v)` = `"v8 d2ffe09"` or `"version unknown"`.
- `bot/shape.lua`: pure shape math in world coordinates (the brain loads it for splits): `ball(x,y,z,d)`, `cylinder(x,z,d,y1,y2)`, `box(...)`, `cut(s, top, bottom)` (nil when nothing is left), `inside`, `line(s, y, x, z)` (the run along z for a given x, or along x for a given z), `ranges(s, fill, y, x, z)` (what to build: `solid`; `hollow` = blocks with any side out; `walls` = a horizontal side out; a cut is open, not a lid), `counts`, `share`, `axes`, `lowHalf`. Round shapes: a block is in when its distance to the center is at most (d-1)/2 (the user's 75-block chart, bumps included), in half blocks so even diameters (centered between blocks) work: limit (d-1)^2 + 1 for a disk, + 2 for a ball. The middle level of a ball is the circle of the same diameter.
- `bot/build.lua`: `buildSphere`/`buildBox` with one block type, bottom-up: the turtle flies one block above the level and places down. A share is a tile: a run of columns across the longer side, and for hollow/walls one half of the other side, so a share is one patch of surface. The turtle only moves inside its tile at most two blocks above the level it builds; every other move (start, refills, after a reboot) `fly`s straight up to two above the structure, across, and down. `nav.keep` = the build block, so no move can break the structure (seen in a test: direct travel instead of `fly` fails with "protected block in the way" instead of digging). Supply: `home` (an inventory next to home, any side) or `"x,y,z"` (taken from the block above it); refused if it is under the structure. A block already in place counts as kept, anything else is dug, protected blocks are skipped (results: placed, kept, skipped, trips). Ends two above the structure, so a following goHome flies over it. Checkpoint per block: level, index, the level's direction.
- `bot/registry.lua`: what the dashboard knows: one record per turtle from `status`/`progress`/`accepted`/`result` messages plus a 200-line event log; a turtle silent for 60 s shows as lost. Logs the version on join (`#7 miner joined, v8 d2ffe09`) and when it changes (`#7 now runs v9 ...`, back from an update). `reg.turtles` has the `label/state/pos/job` shape `bot/fleet.lua` reads. No rednet or screen calls: callers pass messages and times in.
- `tests/`: fake CC world (`fakecc.lua`: turtles, events, `parallel`, rednet, virtual time, fake terminal and monitors via `sim.useTerm`/`sim.addMonitor`) and tests (`tests.lua`, which also runs `ui_tests.lua`, `registry_tests.lua` and `dash_tests.lua`) run with `python tests/run.py` (needs `pip install lupa`). `shape_tests.lua` covers shapes (brute-force shells), mineSphere and building; the sim has `place*`/`suck*` and `sim.placeLog`. `sim.spawn(id, ...)` adds a second turtle with its own APIs and module copies (`t.require`), so two real `nav`s can meet in one world. The rednet side of the fleet is tested one side at a time (real worker vs scripted brain, real brain vs scripted turtles); the dashboard runs beside a driver coroutine that types, touches the monitor and plays the turtles. Looks (`detect`, `inspect`) take a tick like in the game but are not actions; `sim.onDetect(t, x, y, z)` runs after one, e.g. to move a turtle off before the next command. Reboots: `sim.terminateAtAction` (after any turtle action) or `sim.onMove` raise "Terminated", `sim.reboot()` clears modules and events but keeps files and the world. Not installed on turtles.

## Conventions
- Comment blocks include a `<Codex>` tag.
- Secrets never go in the repo: `/.openrouter_key`, `/.github_token` are created by hand on each machine.
- LLM tools are injected as `{ name = { description, parameters (JSON schema), handler(args) -> table, final? } }`. Each entry point has one: `runPlan` (brain) or `runPlans` (fleet).
- Skills are declared once in `bot/skills.lua` as `{ name, doc, args = { { argName, type, default, hidden? } }, run(args) -> table, split? }`. `hidden = true` (needs a default) keeps an arg out of the prompt: set by `split`, like the round and build skills' `part`/`parts`. `optional = true` (no default) may be left out: the skill gets nil (mineSphere's `top`/`bottom`). Types: `int`, `count` (>= 1), `str`, enum `a|b|c` (`dir` = 8 horizontal directions). Arg names shared between skills must have compatible types (the schema merges them). Keep `doc` short: it is sent on every call. `split(args, positions)` (optional) runs on the brain and returns args per turtle (nil = that turtle skips the step); it must not touch the turtle API.
- Skills must survive a reboot mid-step: `run(args, ctx)` may run again from the start of the step with `ctx.state` = whatever it last passed to `ctx.save` (nil on a fresh start). Either be safe to repeat (goTo, goHome, unload) or save enough first: `move`/`face` save their resolved target before acting, `mineArea`/`mineBox` checkpoint after every cell.
- Results are compact tables with an `ok` field; errors are returned (`{ ok = false, error = ... }`), never thrown out of the loop. Exception: `"Terminated"` (Ctrl+T) is always re-raised past every `pcall`.
- `bot/nav` functions return `ok, err` and never throw; skills turn failures into results.
- Use `textutils.json_null` where the API needs a real JSON `null`.
- The LLM decides *what* to do; pathfinding, refueling, inventory and coordinates stay in Lua.
- Lua must run on CC's Cobalt VM (Lua 5.2): no `//`, no bitwise operators, no `goto`.
- Turtles must be labeled (`label set ...`) or they lose files when broken.

## Resume (reboots, chunk unloads, server restarts)
- Needs `startup.lua` on every turtle (`shell.run("worker")`) and on the brain computer (`shell.run("fleet resume")`, or `shell.run("fleet dash")`, which resumes a saved job by itself), and GPS on the turtles to be exact.
- Worker: a job is saved when accepted; plan.run journals each step; mining checkpoints after every cell (direction, layout, origin, start heading, next cell, counters). After a reboot `mineArea`/`mineBox` first rejoin their route (inside the box, beside it, on the approach, or anywhere on a trip home), then go on. Results are kept until acked.
- Nav markers in `/nav_state.json` make every reboot point recoverable: `turning` (set during a turn: the saved heading may be one turn off) and `calibrating` (`{ pos, heading }` from before a calibration, kept until the turtle is back there). `init(trustSaved)`: when resuming a job and the saved state is consistent (GPS within 1 block of the saved spot, no marker), no calibration moves at all. Otherwise it calibrates: horizontally where it stands, else one block up or down, else (resuming only) by digging one block. A cut-off calibration is undone (same level first, then back to the spot and facing). If the heading still can't be known, it stays unknown and moves fail instead of guessing.
- Stress-tested in the sim: 1,000+ random jobs, ~13,000 reboots at random actions. Every box ended fully dug, nothing else dug and the turtle in the right place and facing, except ~4% of the jobs where a reboot right after a turn caught the turtle boxed in: one extra block dug (the last-resort calibration in `nav.init`), always next to the box. The sim reboots right after turns far more often than a real server would. Re-measured 2026-10-03 with per-cell junk drops: 39 of 1,000 jobs (13,012 reboots), all that one dig; 30 of 1,000 (11,216 reboots) before, the same rate per reboot. The 30-job test in `tests/tests.lua` allows that one block (it passed before only because its seeds missed it). 2026-10-05, mineSphere and builds through the worker (every share of a shape in one plan): 357 random jobs, 16,358 reboots, all exact (4 with that one dig). That run found a bug since fixed: `nav.init` saved during a calibration before loading home, so two reboots in a row during calibrations lost home (the turtle then made its current spot home); `init` now loads home first.

## Known limitations
- `http.post` blocks only the coroutine that calls it; under `parallel`, other coroutines keep getting every event. The fleet brain calls the LLM and waits for rednet in one coroutine, so it only calls the LLM when every turtle is idle. Two LLM calls in flight at once would need unique request keys (`http_success` matches by URL only).
- Fleet replans only once every turtle has finished: a turtle that fails early idles until the slowest one is done.
- Dashboard: goals, `/home`, `/refuel`, `/sethome`, `/update` and resume run one at a time (the brain saves a single job in `/fleet_job.json`), so a second goal is refused while one runs and `/home <id>` is refused too (`/home` for all stops the goal first). Stopping one turtle (`/stop 3` or its button) fails only its part; once the others finish the LLM is asked to replan (one call). `/stop` for all ends the goal with no replanning. LLM call and token counters add up when a goal ends, not live; log lines are cut at the screen width. `/exit` or Ctrl+T quits the dashboard but leaves turtles running (see `bot/dash.lua`). Color and touch need an advanced monitor. Sim-tested only: real monitor sizes, touch and key events are unverified in-game.
- Turtle meetings are resolved locally (right of way by id, step aside, makeway), with no lanes or reservations. Known failure: the yielding turtle's side cell is exactly where the other turtle's path turns next; the yielder then can't get back and its step fails after `turtleWaits` (mining then rejoins its route and retries, see `patiently`). Jams of 3+ turtles are sim-untested (32 turtles work in-game). A turtle that never moves (not a worker, or busy and stuck) fails one step after ~20 s; mining and travel retry for ~5 min before failing (`config.turtleRetries`).
- Untested in-game: whether a turtle can read an adjacent turtle's id via `peripheral.call(side, "getID")`. If not, the coin flip takes over (slower, still tested).
- Fleet turtles must stay in modem range (wireless ~64 blocks; ender modems have no limit). A turtle in an unloaded chunk is frozen; it resumes when the chunk loads again, and the brain waits up to 10 minutes for it.
- A stop abandons the running command; the worker resyncs with `nav.init()`, which needs GPS to be exact.
- Rednet is not authenticated: anyone on the server could send plans to the workers.
- Plans are open-loop: no step can feed an observation back to the model except by failing.
- Junk is dropped once per mined cell, not after every dig: a drop is a turtle command that plays an 8-tick wait (`TurtleDropCommand` plays `WAIT`; `TurtleBrain` runs no command while an animation plays), as long as a move. A cell is about 41 ticks, so per-cell dropping costs ~20% (one drop when the cell's junk is one item type), per-dig up to ~60%. The user chose per-cell (2026-10-03).
- Dropped junk becomes item entities (despawn after 5 min), about one per mined cell (neighbouring cells are 1 block apart, too far to merge): roughly 120 alive per digging turtle, so tens of turtles keep a few thousand around the dig. If the server lags, batching again (drop only when the inventory fills) brings it back to a few per turtle. The junk list is config-only; the LLM can't say "keep the stone" per job.
- Ores stay in the turtle at the end of a dig unless the plan ends with `goHome` + `unload`.
- Round digs: `mineCircle`/`mineSphere` dig one block above the door (the approach step, like `mineBox` above its corner): air when the hole starts at the surface. A shape under the ground also needs the access shaft from the surface down to its top (goTo digs it). A whole ball's (or anything above its middle) top level is small: every share enters through it, so the fleet queues there at first. Shares are always runs of x columns: turtles lined up along z still get them west to east by x. With many turtles a share is 2-3 columns, so a middle column of 75 blocks makes shares up to ~50% uneven. No ellipses (non-square ovals) and no rings (hollow circles) to dig.
- Building: needs open space above the structure (it flies two blocks above it) and a supply chest holding only the build block (and fuel): turtle.suck takes slots in order. Travel at the building level digs other blocks in the way (terrain inside the tile), never the build block itself. A build block that is also fuel (coal_block, dried_kelp_block) would be burned by `nav.refuel`. Falling blocks (sand, gravel) fall where nothing is below them (hollow shapes). Blocks are placed facing whatever way (stairs, logs). A supply at x,y,z serves one turtle at a time (the others wait their turn). Hollow balls need a big storage (any inventory block works): 50 wide = 6,096 blocks (96 stacks), 100 wide = 25,256 (395 stacks), 200 wide = 102,696 (1,605 stacks).
- `brain` (single turtle) does not resume after a reboot; only `worker` jobs do. `mined` counts can be a little low after reboots (digs after the last checkpoint are not counted again).
- No fuel pickup: turtles only burn fuel they carry or dig up (or set `need_fuel = false`).
- `refuelAll` (before every unload, before a trip home, the `refuel` skill) burns anything combustible, wood included, up to the fuel limit: coal reaches a chest only once the tank is full.
- `update` needs workers that already have it: turtles installed before it (2026-10-03) must run `install` by hand once (then reboot). Each turtle fetches from GitHub itself (a private repo needs `/.github_token` on every turtle), but at the sha the brain gave it, so only the brain uses an API call.
- `goTo` walks axis by axis and digs through whatever is in the way (protected blocks excepted); no pathfinding around obstacles.
- `init()` steps the turtle 1 block and back on every start when GPS is available (heading calibration, 2 fuel), except a worker resuming a job with a consistent saved state.
- Without GPS, coordinates are relative to the first run and "north" is the turtle's first facing.
- The test world is a simplified CC. In-game: single-turtle `brain` + `mineArea` confirmed working (2026-10-03); `mineBox`, `worker`, `fleet` and resume not yet.
- Model choice: `deepseek/deepseek-chat` (DeepSeek V3, 2 providers) ran without error but came back empty with no tool call (2026-10-03).
